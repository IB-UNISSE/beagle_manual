Uso básico de Slurm

¿Qué es Slurm?

Slurm es un sistema de administración de trabajos para servidores y clústeres de cómputo. Su función es organizar el uso de los recursos disponibles, como CPUs, memoria RAM, tarjetas GPU y tiempo de ejecución.

En lugar de ejecutar análisis pesados directamente en la terminal, los usuarios envían sus trabajos a una cola mediante Slurm. El sistema decide cuándo y dónde correrlos, de acuerdo con los recursos solicitados y la disponibilidad de los nodos.

Esto ayuda a:

  • evitar que una sola persona sature el servidor;

  • organizar los análisis de varios usuarios;

  • asignar CPUs, memoria y GPUs de manera controlada;

  • dejar registro de los trabajos ejecutados;

  • mejorar la reproducibilidad de los análisis.

Particiones disponibles para usuarios del IB-UNAM

En Atocatl existen varias particiones de Slurm. Sin embargo, para los usuarios del Instituto de Biología, UNAM, las particiones principales de interés son:

Partición Nodo(s) Recursos principales Uso recomendado
ib beagle-01, beagle-02 CPUs y memoria RAM Trabajos generales de bioinformática con CPU
gpu_V100 beagle-gpu-01 80 CPUs, ~754 GB RAM y 3 GPUs NVIDIA V100 Trabajos que requieren GPU o análisis grandes que necesitan muchos CPUs y memoria

Puedes revisar el estado de estas particiones con:

sinfo -p ib,gpu_V100

Una salida esperada puede verse así:

PARTITION AVAIL  TIMELIMIT  NODES  STATE NODELIST
ib           up 5-00:00:00      2   idle beagle-[01-02]
gpu_V100     up   infinite      1   idle beagle-gpu-01

Para ver los recursos disponibles por nodo:

sinfo -N -p ib,gpu_V100 -o "%N %c CPUs %m MB %G %T"

Ejemplo de salida:

NODELIST       CPUS  MEMORY MB  GRES   STATE
beagle-01      32    96064      (null) idle
beagle-02      20    192616     (null) idle
beagle-gpu-01  80    772109     gpu:3  idle

Esto indica que:

  • beagle-01 tiene 32 CPUs y aproximadamente 94 GB de RAM.

  • beagle-02 tiene 20 CPUs y aproximadamente 188 GB de RAM.

  • beagle-gpu-01 tiene 80 CPUs, aproximadamente 754 GB de RAM y 3 GPUs NVIDIA V100.

Por esta razón, la partición gpu_V100 puede ser útil para trabajos que requieren GPU, pero también representa el nodo con mayor capacidad de CPU y memoria dentro de BEAGLE.

Conceptos básicos

Job

Un job es un trabajo enviado a Slurm. Puede ser un script de Bash que ejecuta un análisis bioinformático, un programa de R, Python, Apptainer, BLAST, IQ-TREE, MAFFT, BEAST, RevBayes, entre otros.

Cola

La cola es la lista de trabajos que están esperando, corriendo o terminando dentro del sistema Slurm.

Partición

Una partición es una sección lógica del clúster. En este caso, las particiones principales para usuarios del IB-UNAM son:

ib
gpu_V100

Usar una partición significa indicar en qué grupo de nodos quieres ejecutar tu trabajo.

Por ejemplo:

#SBATCH -p ib

significa:

enviar mi trabajo a la partición ib.

Mientras que:

#SBATCH -p gpu_V100

significa:

enviar mi trabajo a la partición con GPU V100.

Recursos

Cuando envías un trabajo, debes indicar los recursos que necesitas. Por ejemplo:

  • número de CPUs;

  • memoria RAM;

  • tiempo máximo de ejecución;

  • nombre del trabajo;

  • partición donde se ejecutará;

  • número de GPUs, si aplica.

Comandos básicos

Ver el estado del clúster

sinfo

Ver solo las particiones del IB-UNAM

sinfo -p ib,gpu_V100

Estados comunes de los nodos

Estado Significado
idle El nodo está libre
alloc El nodo está ocupado
mix El nodo tiene algunos recursos ocupados y otros libres
down El nodo no está disponible
drain El nodo no acepta nuevos trabajos

Ver trabajos en cola

squeue

Ejemplo:

JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
1234        ib  analisis cristian  R       1:23      1 beagle-01

Estados comunes de los trabajos

Estado Significado
R Running, el trabajo está corriendo
PD Pending, el trabajo está esperando
CG Completing, el trabajo está terminando
CD Completed, el trabajo terminó correctamente
F Failed, el trabajo falló
CA Cancelled, el trabajo fue cancelado

Ver solo tus trabajos

squeue -u $USER

Cancelar un trabajo

scancel JOBID

Ejemplo:

scancel 1234

Cancelar todos tus trabajos

Usar con cuidado:

scancel -u $USER

Primer ejemplo: ejecutar un comando simple

Puedes probar Slurm ejecutando el comando hostname en la partición ib:

srun -p ib -N1 -n1 hostname

La salida esperada será el nombre de alguno de los nodos asignados, por ejemplo:

beagle-01.lamod.unam.mx

o:

beagle-02.lamod.unam.mx

Esto significa que Slurm ejecutó el comando en uno de los nodos de la partición ib.

Enviar trabajos con sbatch

La forma recomendada de usar Slurm es crear un script y enviarlo con:

sbatch script.sh

Un script de Slurm es un archivo de Bash con instrucciones especiales que empiezan con:

#SBATCH

Estas líneas le dicen a Slurm qué recursos necesitas.

Script mínimo de ejemplo para CPU

Crea un archivo llamado prueba_slurm.sh:

nano prueba_slurm.sh

Contenido:

#!/bin/bash
#SBATCH -J prueba
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 2
#SBATCH --mem=4G
#SBATCH --time=00:05:00

echo "Inicio: $(date)"
echo "Host: $(hostname)"
echo "Job ID: $SLURM_JOB_ID"
echo "Nombre del trabajo: $SLURM_JOB_NAME"
echo "CPUs asignadas: $SLURM_CPUS_PER_TASK"

sleep 10

echo "Fin: $(date)"

Enviar el trabajo:

sbatch prueba_slurm.sh

Slurm responderá algo como:

Submitted batch job 1234

Revisar la salida del trabajo

Por defecto, Slurm crea un archivo llamado:

slurm-JOBID.out

Por ejemplo:

cat slurm-1234.out

Personalizar el nombre de salida

Es recomendable guardar las salidas y errores en una carpeta llamada logs.

Crear la carpeta:

mkdir -p logs

Ejemplo de script:

#!/bin/bash
#SBATCH -J prueba
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 2
#SBATCH --mem=4G
#SBATCH --time=00:05:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

echo "Inicio: $(date)"
echo "Host: $(hostname)"
echo "Job ID: $SLURM_JOB_ID"
echo "Fin: $(date)"

Donde:

Código Significado
%x Nombre del trabajo
%j ID del trabajo

Así se generan archivos como:

logs/prueba_1234.out
logs/prueba_1234.err

Parámetros principales de Slurm

Opción Significado
#SBATCH -J nombre Nombre del trabajo
#SBATCH -p ib Partición donde se ejecuta
#SBATCH -N 1 Número de nodos
#SBATCH -n 1 Número de tareas
#SBATCH -c 4 CPUs por tarea
#SBATCH --mem=16G Memoria solicitada
#SBATCH --time=01:00:00 Tiempo máximo
#SBATCH -o archivo.out Archivo de salida estándar
#SBATCH -e archivo.err Archivo de error
#SBATCH --gres=gpu:1 Solicitar una GPU, cuando aplique

¿Cuántas CPUs pedir?

No siempre conviene pedir muchas CPUs. Solo deben solicitarse más CPUs si el programa realmente puede usarlas.

Ejemplos:

Programa de un solo hilo

#SBATCH -c 1

Programa con 4 hilos

#SBATCH -c 4

Programa con 16 hilos

#SBATCH -c 16

Además, dentro del comando del programa hay que indicar el mismo número de hilos usando la variable:

$SLURM_CPUS_PER_TASK

Ejemplo con fastp:

fastp \
  -i muestra_R1.fastq.gz \
  -I muestra_R2.fastq.gz \
  -o limpia_R1.fastq.gz \
  -O limpia_R2.fastq.gz \
  -w $SLURM_CPUS_PER_TASK

Ejemplo con iqtree2:

iqtree2 -s alineamiento.phy -T $SLURM_CPUS_PER_TASK

Ejemplo con mafft:

mafft --thread $SLURM_CPUS_PER_TASK entrada.fasta > alineado.fasta

Ejemplo para un programa bioinformático en CPU

Archivo sugerido:

mafft_test.sh

Contenido:

#!/bin/bash
#SBATCH -J mafft_test
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 8
#SBATCH --mem=16G
#SBATCH --time=02:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "===================================="
echo "Trabajo: $SLURM_JOB_NAME"
echo "Job ID: $SLURM_JOB_ID"
echo "Usuario: $USER"
echo "Host: $(hostname)"
echo "Inicio: $(date)"
echo "CPUs asignadas: $SLURM_CPUS_PER_TASK"
echo "Directorio de envío: $SLURM_SUBMIT_DIR"
echo "===================================="

mafft --thread $SLURM_CPUS_PER_TASK \
  datos/secuencias.fasta \
  > resultados/secuencias_alineadas.fasta

echo "===================================="
echo "Fin: $(date)"
echo "===================================="

Enviar:

sbatch mafft_test.sh

Ejemplo con Apptainer en CPU

Si el análisis usa un contenedor de Apptainer, puedes usar la partición ib.

#!/bin/bash
#SBATCH -J apptainer_cpu
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 4
#SBATCH --mem=8G
#SBATCH --time=01:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "Inicio: $(date)"
echo "Host: $(hostname)"
echo "Job ID: $SLURM_JOB_ID"

apptainer exec programa.sif programa --help

echo "Fin: $(date)"

Ejemplo con carpetas enlazadas en Apptainer

Cuando se trabaja con contenedores, es útil enlazar la carpeta actual como /work dentro del contenedor.

#!/bin/bash
#SBATCH -J apptainer_cpu
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 4
#SBATCH --mem=8G
#SBATCH --time=01:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "Inicio: $(date)"
echo "Host: $(hostname)"

apptainer exec \
  --bind $PWD:/work \
  --pwd /work \
  programa.sif \
  programa input.fasta output.txt

echo "Fin: $(date)"

Ejemplo para usar la partición con GPU V100

Para trabajos que requieren GPU, se debe usar la partición:

gpu_V100

Un script básico puede verse así:

#!/bin/bash
#SBATCH -J gpu_test
#SBATCH -p gpu_V100
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 4
#SBATCH --mem=16G
#SBATCH --gres=gpu:1
#SBATCH --time=01:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "===================================="
echo "Trabajo: $SLURM_JOB_NAME"
echo "Job ID: $SLURM_JOB_ID"
echo "Usuario: $USER"
echo "Host: $(hostname)"
echo "Inicio: $(date)"
echo "CPUs asignadas: $SLURM_CPUS_PER_TASK"
echo "Nodo asignado: $SLURM_JOB_NODELIST"
echo "===================================="

nvidia-smi

echo "Fin: $(date)"

Enviar:

sbatch gpu_test.sh

Si el trabajo se ejecuta correctamente, el archivo de salida debe mostrar información de la GPU NVIDIA V100 disponible en el nodo asignado.

echo "Job ID: $SLURM_JOB_ID"

Buenas prácticas

1. No correr análisis pesados directamente en la terminal

Evita ejecutar programas pesados directamente en el nodo de acceso:

iqtree2 -s archivo.phy -T 32

En su lugar, crea un script y envíalo con:

sbatch script.sh

2. No pedir más CPUs de las necesarias

Si un programa solo usa 4 hilos, no pidas 32 CPUs.

Mal:

#SBATCH -c 32

Bien:

#SBATCH -c 4

3. Usar la partición correcta

Para trabajos generales con CPU:

#SBATCH -p ib

Para trabajos con GPU V100:

#SBATCH -p gpu_V100
#SBATCH --gres=gpu:1

4. Siempre usar carpetas organizadas

Ejemplo:

proyecto/
├── datos/
├── scripts/
├── resultados/
└── logs/

5. Guardar salidas y errores

Usa:

#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

6. Probar primero con datos pequeños

Antes de enviar un análisis grande, prueba con un subconjunto de datos para asegurarte de que el comando funciona correctamente.

7. Revisar los logs

Si un trabajo falla, revisa primero:

cat logs/nombre_JOBID.err
cat logs/nombre_JOBID.out

También puedes revisar los archivos con:

less logs/nombre_JOBID.err
less logs/nombre_JOBID.out

Plantilla recomendada para usar CPU y RAM en ib o gpu_V100

Esta plantilla sirve para trabajos que usan principalmente CPUs y memoria RAM. Puede utilizarse en la partición ib para análisis generales, o en la partición gpu_V100 cuando se requiere más capacidad de CPU y memoria RAM.

Para trabajos normales con CPU se recomienda usar:

#SBATCH -p ib

Para trabajos muy grandes que necesitan más CPUs o mucha memoria RAM, pero no necesariamente GPU, puede usarse:

#SBATCH -p gpu_V100

Plantilla:

#!/bin/bash
#SBATCH -J nombre_del_analisis
#SBATCH -p ib
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 8
#SBATCH --mem=32G
#SBATCH --time=04:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "===================================="
echo "Trabajo: $SLURM_JOB_NAME"
echo "Job ID: $SLURM_JOB_ID"
echo "Usuario: $USER"
echo "Host: $(hostname)"
echo "Inicio: $(date)"
echo "CPUs asignadas: $SLURM_CPUS_PER_TASK"
echo "Directorio de envío: $SLURM_SUBMIT_DIR"
echo "Nodo asignado: $SLURM_JOB_NODELIST"
echo "===================================="

# Aquí va el comando principal del análisis
# Ejemplos:
# mafft --thread $SLURM_CPUS_PER_TASK datos/secuencias.fasta > resultados/secuencias_alineadas.fasta
# iqtree2 -s datos/alineamiento.phy -T $SLURM_CPUS_PER_TASK
# Rscript scripts/analisis.R

echo "Aquí va el análisis"

echo "===================================="
echo "Fin: $(date)"
echo "===================================="

Para usar esta misma plantilla en el nodo beagle-gpu-01 solo con CPU y RAM, cambia la partición:

#SBATCH -p gpu_V100

Por ejemplo:

#SBATCH -p gpu_V100
#SBATCH -c 32
#SBATCH --mem=200G

Plantilla recomendada para usar GPUs en gpu_V100

Esta plantilla debe usarse cuando el análisis requiere GPUs NVIDIA V100. En este caso se debe usar la partición gpu_V100 y solicitar explícitamente el número de GPUs necesarias.

Para solicitar una GPU:

#SBATCH --gres=gpu:1

Plantilla:

#!/bin/bash
#SBATCH -J nombre_gpu
#SBATCH -p gpu_V100
#SBATCH -N 1
#SBATCH -n 1
#SBATCH -c 8
#SBATCH --mem=32G
#SBATCH --gres=gpu:1
#SBATCH --time=04:00:00
#SBATCH -o logs/%x_%j.out
#SBATCH -e logs/%x_%j.err

set -euo pipefail

mkdir -p logs resultados

echo "===================================="
echo "Trabajo: $SLURM_JOB_NAME"
echo "Job ID: $SLURM_JOB_ID"
echo "Usuario: $USER"
echo "Host: $(hostname)"
echo "Inicio: $(date)"
echo "CPUs asignadas: $SLURM_CPUS_PER_TASK"
echo "Nodo asignado: $SLURM_JOB_NODELIST"
echo "GPUs asignadas: ${SLURM_GPUS:-No disponible}"
echo "===================================="

echo "Revisando GPU disponible:"
nvidia-smi

# Aquí va el comando principal del análisis con GPU
# Ejemplo general:
# programa_gpu --threads $SLURM_CPUS_PER_TASK

echo "Aquí va el análisis con GPU"

echo "===================================="
echo "Fin: $(date)"
echo "===================================="

Si el análisis usa un contenedor de Apptainer con GPU, se debe agregar la opción --nv:

apptainer exec \
  --nv \
  --bind $PWD:/work \
  --pwd /work \
  programa_gpu.sif \
  programa_gpu input.fasta output.txt

La opción --nv permite que el contenedor detecte las GPUs NVIDIA disponibles en el nodo.

¿Qué pasa si solicito menos o más recursos de los necesarios?

Cuando se envía un trabajo a Slurm, los recursos solicitados deben ser lo más cercanos posible a lo que realmente necesita el análisis. Pedir menos recursos puede hacer que el trabajo falle o tarde demasiado. Pedir recursos de más puede hacer que el trabajo espere más tiempo en la cola y que otros usuarios no puedan usar esos recursos.

Si solicitas menos recursos de los necesarios

Menos CPUs de las necesarias

Si pides pocas CPUs, el análisis puede correr más lento.

Por ejemplo:

#SBATCH -c 2

pero el programa podría funcionar mejor con 8 CPUs:

mafft --thread 8 entrada.fasta > salida.fasta

En este caso hay un problema: el script pidió 2 CPUs, pero el programa intenta usar 8. Esto puede saturar el nodo o hacer que Slurm limite el trabajo, dependiendo de la configuración del sistema.

Lo correcto es que el número de CPUs solicitado coincida con el número de hilos usados por el programa:

#SBATCH -c 8

y dentro del comando:

mafft --thread $SLURM_CPUS_PER_TASK entrada.fasta > salida.fasta

Menos memoria de la necesaria

Si pides menos memoria RAM de la que necesita el análisis, el trabajo puede fallar.

Por ejemplo:

#SBATCH --mem=4G

pero el análisis necesita 20 GB de RAM.

En ese caso, Slurm o el sistema pueden terminar el trabajo automáticamente. El error puede aparecer en los archivos .err o .out con mensajes como:

Out Of Memory
oom-kill
Killed

o el trabajo puede aparecer como fallido en Slurm.

Menos tiempo del necesario

Si pides menos tiempo del que necesita el análisis:

#SBATCH --time=00:30:00

pero el programa necesita 2 horas, Slurm cancelará el trabajo cuando se cumpla el tiempo máximo.

El trabajo puede aparecer con estado:

TIMEOUT

o como cancelado por límite de tiempo.

Si solicitas más recursos de los necesarios

Pedir más recursos de los que realmente usa el análisis no hace que el programa corra más rápido automáticamente.

Por ejemplo, si pides:

#SBATCH -c 32
#SBATCH --mem=200G

pero tu programa solo usa 4 CPUs y 10 GB de RAM, los recursos restantes quedan reservados para tu trabajo aunque no se estén usando.

Esto puede provocar que:

  • tu trabajo tarde más en iniciar porque Slurm necesita encontrar un nodo con muchos recursos libres;

  • otros usuarios no puedan usar esas CPUs o memoria mientras tu trabajo está corriendo;

  • se desperdicie capacidad del clúster;

  • se reduzca la eficiencia general del sistema.

En algunos sistemas, además, el uso de recursos puede afectar métricas de prioridad o reportes de consumo, aunque el programa no haya usado todo lo solicitado.

Ejemplo de mala práctica

#SBATCH -p ib
#SBATCH -c 32
#SBATCH --mem=100G

pero el comando ejecutado es:

iqtree2 -s alineamiento.phy -T 4

Aquí se reservaron 32 CPUs, pero IQ-TREE solo usará 4. Las otras 28 CPUs quedan apartadas sin utilizarse.

Ejemplo correcto

#SBATCH -p ib
#SBATCH -c 4
#SBATCH --mem=16G

y el comando:

iqtree2 -s alineamiento.phy -T $SLURM_CPUS_PER_TASK

En este caso, Slurm asigna 4 CPUs y el programa usa esas mismas 4 CPUs.

Recomendación práctica

Si no sabes cuántos recursos necesita tu análisis, empieza con una prueba pequeña.

Por ejemplo:

#SBATCH -c 4
#SBATCH --mem=16G
#SBATCH --time=01:00:00

Después revisa si el trabajo terminó correctamente. Si falló por memoria, aumenta la memoria. Si tardó demasiado pero no falló, puedes aumentar el tiempo. Si el programa permite usar más hilos, puedes aumentar CPUs de forma razonable.

Regla general

Situación Consecuencia
Pedir menos CPUs El análisis puede tardar más
Pedir menos memoria El trabajo puede fallar por falta de RAM
Pedir menos tiempo Slurm puede cancelar el trabajo por límite de tiempo
Pedir más CPUs de las usadas Se desperdician CPUs reservadas
Pedir más memoria de la usada Se bloquea memoria que otros usuarios podrían usar
Pedir GPU sin usarla Se reserva una GPU innecesariamente
Usar más hilos de los solicitados Puede saturar el nodo o violar las buenas prácticas de uso
